# 去 AI 化处理 (de-ai-ify)

## 概述

文件正式提交使用前，做一次去 AI 化清洗。核心目标：让人看不出这是 AI 写的。

**只减不增**：清洗只做删除和替换，不追加任何解释、补充、润色。

## 何时使用

- Markdown 文档提交前
- 协作平台文档发布前
- 邮件/报告发送前
- 任何文本需要「看起来像人写的」

## 场景参数

调用时可指定发布场景，不同场景走不同的清洗策略：

| 场景 | 策略说明 |
|------|---------|
| 公众号文章 | 保持段落节奏，适度保留个人语气，去重结构化连接词 |
| 小红书/社媒 | 短句优先，保留口语化表达，去除固定模板句式 |
| 论文/学术汇报 | 保留正式语气，只去模板结构（首先/其次/综上所述），不动专业术语 |
| 工作日报/周报 | 最轻量处理，删废话、删加粗、删路径痕迹，不碰正文主体 |
| 不指定（默认） | 全流程清洗 |

场景参数影响的是清洗力度和保留度，不改变内容本身。

## 清洗流程

逐层过，每层扫完再进下一层：

### 第一层：AI 语言特征（全删/替换）

| 类别 | 目标 | 操作 |
|------|------|------|
| 结构化连接词 | 「首先/其次/最后」「总而言之」「综上所述」 | 直接删 |
| 过度强调 | 「值得注意的是」「需要特别指出的是」「尤其关键的是」 | 直接删 |
| 重复解释 | 「也就是说」「换句话说」「即」（同一意思换说法） | 删后面那句 |
| 万能铺垫 | 「在当今……背景下」「随着……深入」「可以预见」 | 整句删 |
| 面面俱到 | 每个角度都覆盖、优缺点各说一遍的平衡论述 | 只留最核心的 |
| 无效总结 | 结尾重复前面说过的 | 删结尾总结段 |
| 解决方案式叙事 | 「XX 问题可以从以下维度看：…因此，应该…」 | 去掉分析框架，直接给结论 |
| 过度绝对化 | 「唯一」「绝对是」「毫无疑问」「必然是」 | 删掉或改为「其中一个」「比较」 |
| 宏大/诗意词汇 | 「觉醒」「重塑」「赋能」「破局」「升维」 | 换成普通人说的词 |
| 加粗标签化 | `**目标**`、`**原则**`、`**不传手机号**` 等用加粗把关键词做成独立标签 | 去加粗，融入自然段落 |

### 第二层：啰嗦精简

- 一个意思说一遍，不说两遍
- 合并短段落，不要让每段都差不多长
- 删掉「这意味着」开头的解释句
- ✅ 「数据不对」 ❌ 「经过分析发现数据存在一定的偏差」

### 第三层：个人痕迹清理

| 痕迹类型 | 示例 |
|----------|------|
| 本地绝对路径 | `{WORKSPACE}/...`、`/Users/{USER}/...` |
| Windows 用户名 | `~/` 中的用户名 |
| 环境变量 | `$HOME`、`%USERPROFILE%`、`~/.config` |
| 内网地址 | `10.x.x.x`、`192.168.x.x` |
| Token/Key | API Key、Token 片段 |
| 个人目录名 | 含个人信息的文件夹名 |

处理：有敏感痕迹 → 脱敏替换为通用占位符（如 `~/project/`）；纯路径引用 → 删掉或替换为相对路径。

### 第四层：结构痕迹打破

- 段落长度差异化，不要让每段 3-4 行
- 能不分点的就别分点，用自然段
- 标题层级可以跳，不用每处都 H2→H3
- 完美对齐的表格、缩进 → 允许微小不齐
- **ASCII 框线流程图**（`┌──┐` 等用 box-drawing 字符画的流程图）：AI 极爱画，真人几乎不画。删掉，用一句话白话说流程
- **穷举式决策/映射表**：把所有 if-then 组合无遗漏列出来（如 高/低意向 × 同意/不同意 = 4 条全写）。真人写需求不会做穷举覆盖，只举 1-2 个典型场景
- **文档元数据头部**：`> 版本：v1.0 | 创建：2026-06-29` 这类制式头部。内部文档直接删，真人不会给自己看的文档写版本号
- **制式表格尾巴**：末尾的「待确认事项」「变更记录」这类软件 release notes 风格表格。真人不会在文档末尾加这个，沟通时口头确认就行

### 第五层：词汇级替换

**AI 中英混排**（非行业术语的情况下）：
| ❌ | ✅ |
|----|----|
| 「这个 task 需要…」 | 「这个任务需要…」 |
| 「先做个 check」 | 「先检查一下」 |
| 「基于这个方案」 | 「按这个方案」 |

**书面用词 → 日常表达**：
| ❌ | ✅ |
|----|----|
| 予以 | 给 |
| 进行 | （能删就删） |
| 基于 | 按/根据 |
| 贯穿 | 一直/整个 |
| 亦 | 也 |

### 第六层：英文 AI 特征

| 类别 | 目标 | 操作 |
|------|------|------|
| 万能开头 | `In conclusion`、`To summarize`、`In summary` | 直接删或改成 `So` |
| 空洞强调 | `It is worth noting that`、`It should be noted that` | 直接删 |
| 模板排比 | `First and foremost`、`Last but not least` | 改成 `First`、`Finally` |
| 冗余连接词 | `Additionally`+`Moreover`+`Furthermore` 连用两个以上 | 只保留一个 |
| 过度正式 | `A plethora of`、`Numerous`、`Utilize`、`Leverage` | 改成 `a lot of`、`many`、`use` |
| 废话插入 | `In order to`、`Due to the fact that` | 改成 `To`、`Because` |
| 被动滥用 | `It was observed that`、`It was decided to` | 改主动语态 |

### 第七层（可选）：注入个人观点

> ⚠️ 此层为用户主动选择，启用时突破「只减不增」原则，不属于默认清洗流程。

AI 最大的一个特征是说不表态的车轱辘话。如果去味后文本仍然「正确但没人味」，可用此层。

仅在以下条件全部满足时启用：
- 用户提供了个人风格样本（过往文章/聊天记录）
- 文本是署名文章/个人博客，不是技术文档/日报

| 去味前 | 注入后 |
|--------|--------|
| 「这个方案能提升转化率」 | 「我之前试过类似方案，转化率确实涨了，但要注意前期成本」 |
| 「建议早点开始」 | 「我自己踩过坑，这东西拖到月底就来不及了」 |

操作：取 1-2 处核心观点，加上「我」字开头 + 简短个人经历/判断。

## 写前预防

去味最高效的方式是源头控制。在项目模板或 AGENTS.md 中提前嵌入去味规则：

```
- 不使用「首先/其次/最后」「综上所述」「值得注意的是」等结构化连接词
- 段落长度要有变化，不要让每段都是 3 行等长
- 能一句话说清的事，不要拆成三点
- 说人话，不要说公文
- 附上你的一篇过往文章作为个人风格参考
```

源头控管比写完再清洗省时 3 倍。

## AI-likeness 自我评分

清洗完成后，用量表自评（0 = 完全像机器，10 = 完全像真人）：

| 维度 | 扣分项 | 满分 | 说明 |
|------|--------|------|------|
| 连接词 | 仍有「首先/其次」「综上所述」类连接词残留 | 3 | 每发现一处扣 0.5 |
| 句式 | 有多句连续同长度句式 | 2 | 段落有明显模板结构减分 |
| 废话 | 有「值得注意的是」「换句话说」类空话 | 2 | 每处扣 0.5 |
| 人味 | 没有任何个人观点/经历/吐槽 | 2 | 仅在启用第七层时评估；未启用第七层时不扣分 |
| 英文特征 | 仍有 In conclusion / It is worth noting 类残留 | 1 | 仅纯英文文本评估，每处扣 0.5 |
| 痕迹 | 有个人路径/Key/用户名残留 | 1 | 每处扣 0.5 |

**合格线：≥ 7 分**。低于 7 分 → 回到对应层重新清洗。

## 边界场景

| 场景 | 行为 |
|------|------|
| 空输入 | 直接返回，提示「无可处理内容」 |
| 纯英文文本 | ✅ 走第六层英文 AI 特征处理 |
| 全是代码 | 跳过 AI 语言特征层，只做痕迹清理和格式检查 |
| 反复 de-ai | 第二次调用时先检查是否已经洗过，避免过度处理导致文本破碎 |
| 只有一句话 | 不做结构层处理，只做词汇替换和痕迹清理 |

## 实战案例

### 案例1：PRD 文档去 AI 化（外呼信息回传同步RB跟进记录）

**来源**：`~/业务-日常运营/业务产品需求/PRD-外呼信息回传RB-第1期.md`（案例原文路径，已脱敏）

原始 AI 生成版 → 用户手动删除了以下 6 类 AI 痕迹：

| 删除内容 | 对应规则 | 说明 |
|----------|----------|------|
| 头部 `> 版本：v1.0 \| 创建：2026-06-29` + 来源引用 | 第四层·文档元数据头部 | AI 会给内部文档加正式版本号/来源，真人不会 |
| ASCII 框线流程图（`┌──┐` 五步流程） | 第四层·ASCII 流程图 | 该文档用一句话「外呼结束→提取字段→生成摘要→生成建议→拼写记录→写入RB」就够 |
| 字段映射规则表（4 条 if-then 穷举） | 第四层·穷举式决策表 | 高/低意向 × 同意/不同意 = 4 条全覆盖，真人只会在沟通时说「高意向同意加微的就推微信，其他的再说」 |
| 待确认事项表（5 行 `# \| 事项 \| 状态`） | 第四层·制式表格尾巴 | todo 直接放脑子里或待办工具清单，不必表格化放在文档末尾 |
| 变更记录表（`日期 \| 版本 \| 变更内容`） | 第四层·制式表格尾巴 | 内部 PRD 不是发版软件，不需要 changelog |
| `**目标**`、`**不传手机号/微信号**` | 第一层·加粗标签化 | 去加粗后「目标：xxx」「不传原始手机号/微信号：xxx」跟自然段融为一体 |

**教训**：AI 写 PRD 的典型病——把内部需求文档当成开源项目的 README 来排版。流程图画成 ASCII art、if-then 做穷举覆盖、末尾挂 changelog 和 pending items 表。删掉这些，文档反而更干净、更易读。

## 内部业务文档：表达习惯清洗（第八层，2026-11-11 新增）

> 适用：给同事/上级看的协作平台业务文档（分析报告、汇报、方案）。来源是 2026-11-11「i8 调研战区差异分析」的实改对照——实际手动删掉的内容，都是这一类毛病。

**核心判据：文档是给读者看的成品，不是给对话对象看的回复。**

### 必删的六类

| 类别 | 典型写法（删） | 为什么 |
|------|--------------|--------|
| **自评自夸** | 「这是全篇最硬的一条」「这是唯一显著差异，也最容易复制」 | 好坏由读者判断，作者不给自己打分 |
| **对话式框架** | 「你的判断部分成立，但有一处要改」「成立的：…／要改的：…」 | 文档面对读者，不面对提需求的人；这类框架还会留下悬空的半句 |
| **版本与过程叙述** | 「上一版用的是 XX，口径不对，已废弃」「本版改用…」 | 只呈现结论；改了什么、错在哪不进正文 |
| **超出数据的推断** | 「说明他们把注意力放在外部竞品上」「说明他们有办法化解」 | 数据只说事实，因果和动机留给读者；要写就写成待验证的问句 |
| **讲课式补注** | 「注意 Model Y 这条要反过来问：…」 | 一段正文后的口头补充，删掉；要留下就并进正文一句话 |
| **不做的建议** | 建议段里写「政策这条线不用按战区拆」 | 建议只写要做什么，不写不用做什么 |

### 要遵守的写法

- **建议标题带依据**：「基于强弱战区对比，话术建议：把充电和续航讲透」，不写「试点只做一件事：…」这类口号式祈使句。
- **建议要可执行、去主观**：「定位相对弱战区（建议山东、四川，样本量足），用强战区的充电价值讲述做指引，对比试点前后占比」。不写「打两周」这类无依据的量化、「最容易复制」这类评价。
- **术语按口径定死**：战区表现这一语境下用「成交」，不用「订单」；标题与正文口径说明必须同一个词。
- **删掉多余的「后续可补」**：只留确实需要补、且读者会用到的。

### 顺带的格式动作

导出 Markdown 底稿后再改，表格分隔行会被写成 `|---|---:|---:|`，用户在协作平台侧改成 `|-|-|-|`。这是导出格式差异，本地底稿保持标准写法即可，不用跟。

### 落地方式（重要）

改完线上文档后，**把用户的改动逐条对照，能归纳成长期规则的写进本节**。这是避免「每次都要用户改很多」的唯一办法：改一次，沉淀一条。
