# goal-gate：Goal 模式就绪闸门

> **一句话**：锁定项目文件夹 → **第 0 步关联合并待办工具相关任务 + 取回引用素材** → 读 goal.md + To-Do 文档.md（+ spec.md）→ 先自盘补全 → 再六维度打分 → 追问确认 → ≥90 分放行 Goal 模式。

## 核心定位

用户想用 Agent 的 Goal 模式自动跑项目，但担心需求没讲清楚会跑偏。本 skill 是**发起 Goal 模式前的最后一道闸门**：量化判定 goal/todo/spec 够不够清楚，不够就追问补到够。

## 执行硬规则：先补后评

> **禁止只打低分不推进。** goal-gate 不是审稿人，而是启动教练：凡是能从现有文件、参考资料、项目上下文、AGENTS.md/Skill 清单中推断或整理出来的内容，必须先补成 `[待确认]` 草稿，再进入评分。

执行时必须遵守：

0. **先组输入再评分（v1.2 新增）**：评分前先跑第 0 步「关联合并 + 取料」——把待办工具里的相关任务并成输入集、把引用的素材取回 `资料文件夹/`；"先补后评"补的是**在手材料**，材料没到就别评分。
1. **先盘点可补项**：交付物、验收标准、执行步骤、取数来源、Skill 清单、参考资料路径，能从现有材料推出来的先补，不得直接写“缺失”。
2. **先写入作业文档**：自补内容优先写回 `goal.md` / `To-Do 文档.md` / `spec.md` 或 `_goal_gate_draft.md`，并标 `[待确认]`。
3. **再评分**：评分必须基于“原文件 + 已自补草稿”，不能只基于原始不完整文件。
4. **再追问**：只问自己补不了或必须用户拍板的内容；用户确认后，把 `[待确认]` 转成正式内容。
5. **低分要带行动**：任何低于 80% 的维度，都必须同时给出“我已补了什么 / 还需要你确认什么”，不能只输出扣分原因。


```
project-folder-init（建文件夹 + goal.md / To-Do 文档.md）
        ↓
goal-gate（第 0 步 关联合并 + 取料 → 自盘补全 → 六维度评分 → 追问 → 复评 → ≥90 放行）
        ↓
≥90 分 → 发起 Goal 模式
```

## 何时使用

**触发词**：
- 「能不能开跑」
- 「清晰度够不够」
- 「能不能进 Goal 模式」
- 「goal-gate」「评分一下」「goal 评分」

**何时用**：项目文件夹已建好（project-folder-init 产出），goal.md / To-Do 文档.md 已有初稿，准备发起 Goal 模式前。**只要有关联的待办工具任务或引用素材，先跑第 0 步。**
**不用**：项目还没建文件夹（先走 project-folder-init）；简单任务不需要 Goal 模式。

## 输入

| 参数 | 说明 |
|------|------|
| **项目文件夹路径** | 必填。`{WORKSPACE}/1、项目/<项目名>/`，或用户说「就这个项目」时从上下文推断 |
| 评分文件 | 固定读 `goal.md` + `To-Do 文档.md`；若存在 `spec.md` 或 `.trae/specs/` 下有 spec（Spec 模式工具产出），一并读入 |
| 关联待办工具任务 | 可选。若本任务来自待办工具（用户甩的是 dida365 链接）或有关联任务线索，第 0 步会去待办工具检索并合并 |

> 若用户只给了项目名没给路径，先到 `{WORKSPACE}/1、项目/` 下匹配文件夹；找不到则停下问用户。

## 评分表（满分 100）

| # | 维度 | 分值 | 满分判据（拿满分要满足） | 0 分判据 |
|---|------|------|----------------------|---------|
| 1 | **交付清单** | 20 | 每个交付物有名称 + 验收标准 + 谁验收 | 没写交付物 |
| 2 | **执行步骤** | 20 | 每步可独立执行 + 前置依赖标清 + 顺序合理 | 只有目标没步骤 |
| 3 | **数据取数** | 20 | **有取数 BRD**（数据需求说清 + 每个字段标了来源表）+ 字段已经 schema/DESCRIBE 实证（非凭名猜）+ 同义字段的取舍理由 + 取数工具（BI 平台/内部数据平台）+ 时间范围 + 拼表键 | 涉及取数却完全没写；或**字段名未实证 / 用错同义字段**；或**数据需求自相矛盾、字段来源说不清** |
| 4 | **目标清晰度** | 15 | 核心目标一句话讲清 + 有验收条件 | 目标缺失 |
| 5 | **Skill 清晰度** | 15 | 知道本次会调用哪些 skill + 参考哪些资料 + 自己的作业文档是哪个 | 完全没提 |
| 6 | **资料完备** | 10 | 参考资料路径已填 + 会议纪要已归位到资料文件夹 | 无任何参考 |

### 维度 3 特殊处理：不涉及取数

当项目**不涉及数据取数**时，维度 3 的 20 分**等比摊到其他 5 项**：

| 维度 | 原分值 | 摊后分值 |
|------|--------|---------|
| 交付清单 | 20 | 25 |
| 执行步骤 | 20 | 25 |
| 目标清晰度 | 15 | 18.75 → 取 19 |
| Skill 清晰度 | 15 | 18.75 → 取 19 |
| 资料完备 | 10 | 12.5 → 取 12 |
| **合计** | 80 | **100** |

> 摊后总分 100（25+25+19+19+12=100）。判定时用摊后分值算 80% 线和 90% 线。

### 维度 3 判定闸门：取数 BRD 是评分对象，不是可选项（v1.4）

> **取数 BRD 是需要被"判定"的东西**——数据需求清不清晰、字段来源清不清晰，都属维度 3 的评分范围。**不是"有 BRD 就满分"，而是 BRD 本身要先过判定。**

对涉及取数的项目，评分前必须先有一份取数 BRD（可由 `goal-to-data-brd` 产出，也可由调用方已有），然后**逐项判定**：

| 判定项 | 满分要求 | 不合格 |
|--------|---------|--------|
| 数据需求是否清晰 | 要回答什么问题、指标清单明列、每指标口径可执行 | 只有模糊描述（"看下数据"）、指标缺失、口径含"大概/相关" |
| 字段来源是否清晰 | 每个字段标了来源表 + 业务含义 + 同义字段取舍理由 | 字段名未实证 / 同义字段混用 / 来源表缺失 |
| 时间范围与粒度 | 起止写死、粒度/维度明确 | 留"最近N天"待定值未归入待确认项 |
| 一致性 | 数据需求与字段口径自洽，无互相矛盾 | 同一问题两个口径并存（如"任务归属人"一处用 `task_owner_id`、一处用 `create_first_store_owner_id`） |

- **四项全过** → 维度 3 才可能拿满分（另需字段已 DESCRIBE 实证）；
- **任一项不合格** → 维度 3 扣分，并把不合格项列入「待确认项」交用户拍板（口径矛盾必须用户选，不擅自定）；
- **不涉及取数** → 走上面的等比摊分，本闸门不适用。

> ⚠️ **禁止"有 BRD 就算通关"**：BRD 存在但需求含糊、字段来源不清，同样判不合格。判定的是"清晰度"，不是"有没有"。

### 维度评分依据来源

| 维度 | 评分依据 |
|------|---------|
| 交付清单 / 执行步骤 / 目标清晰度 | 复用 `task-analyzer` 五要素框架（背景/交付物/交付标准/参考资料/执行建议）+ 拆分判据（效率优先/前置优先/内聚不拆） |
| 数据取数 | 先判定是否「有取数 BRD + BRD 是否清晰」（见上「维度 3 判定闸门」）；再复用 `goal-to-data-brd` 的取数口径标准（表/字段/工具/时间范围/拼表键）+ `sql-development` 的**字段验证三步法**（①schema 文档 → ②已有 SQL 用例 → ③DESCRIBE 实证）。**字段名未实证 = 该条不得满分**；同一业务概念有多个候选字段（如「任务归属人」= `task_owner_id` vs「商机首个门店归属人」= `create_first_store_owner_id`）时，必须在 goal.md 里列出候选 + 选定理由，否则扣分 |
| Skill 清晰度 | 对照 `{WORKSPACE}/AIAgents/skills/` 目录 + AGENTS.md 的 Skill 使用指南，判断有没有标清楚该调哪些 skill |
| 资料完备 | 检查资料文件夹是否有内容 + goal.md「关键信息来源」是否填了路径 |

| 总分 | 动作 |

| **≥ 90** | ✅ 放行 Goal 模式，输出「可以开跑」+ 评分摘要 |
| **80 - 89** | ⚠️ 列出缺口逐条追问 → 补完 → 复评 |
| **< 80** | 🚫 不放行，标出主要缺项，回去补文档后再来评分 |

## 核心流程（6 步）

### 第 0 步：关联合并 + 取料（评分前置，强制）

> **为什么放在评分前**：goal-gate 的「先补后评」只能补**已有材料**。如果相关任务没并进来、引用的素材没取回来，评出来的分是"空气分"——资料完备、执行步骤、Skill 清晰度都会被低估。所以先组输入，再评分。

**两种情况走这一步**：
- **A · 关联任务分散在待办工具**：同一个目标被拆成几条待办工具任务，或项目文件夹只覆盖了其中一部分 → 需要把它们并成一份输入。
- **B · 素材只在链接里**：goal.md / 关联任务引用了协作平台文档、网页、公众号、`tmp` 里的临时件，但 `资料文件夹/` 是空的 → 需要把内容取回来。

**执行动作**：

1. **关联检索（复用 task-analyzer 第 0 步的能力）**
   - 拿到线索（待办工具链接 / 任务标题 / 关键词 / 标签）后，用 `dida task filter --json` 先筛，再 `dida project data <projectId> --json` 拉全集对标题+内容 grep 补漏；
   - 命中的候选**汇成清单给用户确认**（标题 + 清单 + 状态 + 待办工具链接），由用户挑哪些是真正的关联任务（父/同主题/依赖/重复）；
   - 确认后**合并成一个输入集**：关联任务的五要素、参考资料、执行要求并入本轮评分依据，记为 `【关联任务合并】`；
   - **双向互相引用**：本任务「参考资料」附关联任务待办工具链接，同时把本任务链接回写进对方描述（沿用 task-analyzer 的写法）。
   - 检索不到关联任务 → 跳过，直接进第 1 步。

2. **取料（把"引用"变成"在手")**
   - 遍历 goal.md + 关联任务里出现的素材引用，按类型取回并落到项目 `资料文件夹/`：
     | 引用类型 | 取料方式 |
     |---|---|
     | 协作平台文档 / 表格 / 多维表格 | skill `lark-doc` / `lark-sheets` / `lark-base` |
     | 网页 / 博客正文 | skill `defuddle` |
     | 微信公众号文章 | skill `wechat-fetcher` |
     | 本地路径（文件/文件夹） | 直接读取；`tmp` 里的临时件读到即落进 `资料文件夹/`，不留在 `tmp` |
     | 需要入库的取数 | 走 `你的取数编排 skill`（本步只取"已经存在"的资料；真跑 SQL 放到 ≥90 之后的执行链路） |
     | 取数字段（表名/字段名） | **必须实证**：按 `sql-development` 字段验证三步法（schema 文档 → 已有 SQL 用例 → DESCRIBE）确认字段真实存在且语义正确，把结果写进 goal.md 的字段字典；**同义字段必须列出候选+选定理由**，禁止只写字段名不写依据 |
   - 每取一份在 `资料文件夹/` 留一个来源记录（来源链接 + 取回时间），供第 6 维度「资料完备」打分。
   - 取不到的（权限不足 / 链接失效 / 需登录）**列为追问项**，不假装已完备。

**产出（必须落下来，再进第 1 步）**：

```
## 第 0 步输入组装结果

### 关联任务合并
| 关联任务 | 清单 | 关系 | 已并入评分依据 |
|---------|------|------|--------------|
| <标题> | 待跟进 | 同主题 | 五要素 + 参考资料 |

### 已取回的素材
| 引用 | 类型 | 落点 | 状态 |
|------|------|------|------|
| <链接> | 协作平台文档 | 资料文件夹/xxx.md | ✅ 已取回 |
| <链接> | 网页 | — | ⚠️ 取不到（需登录），转追问 |
```

> ⚠️ 若既无关联任务、也无外部引用素材 → 在结果里写「本步无对象」一句话说明，不跳过记录。
> ⛔ **禁止跳过本步直接评分**：只要能推断出有关联任务或引用素材，就必须先组输入。这是 v1.2 新增的强制前置。

### 第 1 步：读取文件 + 上下文盘点

1. 锁定项目文件夹，读 `goal.md` + `To-Do 文档.md`（+ `spec.md` 若存在）
2. 读 `资料文件夹/` 的文件清单，必要时读取关键资料摘要
3. 对照 AGENTS.md / Skill 列表，初步判断会调用哪些 skill
4. 判断是否涉及取数 → 决定用 6 维度还是 5 维度（摊分）
5. 形成“可自补清单”和“必须用户确认清单”

### 第 2 步：先自盘补缺（评分前必做）

评分前必须先自己做一轮盘点和补全：

- 能从 goal.md / To-Do / spec / 参考资料 / 会议纪要中**推断出来**的内容，先补成 `[待确认]` 草稿
- 能从任务类型推断出来的 skill 调用，先补进 “Skill 清晰度” 段
- 能从已有文件路径推断出来的参考资料，先补进 “资料完备” 段
- 能从目标和任务列表拆出来的执行步骤，先补进 To-Do 或 `_goal_gate_draft.md`
- 能从目标推断出取数需求的，先补一份取数 BRD 草稿（或引用已有 BRD），标 `[待确认]`——BRD 是维度 3 的评分对象，不能等用户先给
- 补不了的（缺用户决策、缺业务口径、缺数据源确认）才列入追问清单

自盘产出格式：

```
## 自盘结果

### 我已补上的（请确认）
| 维度 | 补了什么 | 写入哪个文件 |
|------|---------|-------------|
| Skill 清晰度 | 从任务推断需调 sql-development + dip-query-service | goal.md 补了一段 |

### 我补不了的（需你回答）
| 维度 | 问题 |
|------|------|
| 数据取数 | 已补取数 BRD 草稿；待你确认：口径用哪个表、同义字段选哪个（`task_owner_id` vs `create_first_store_owner_id`） |
```

> ⚠️ 自盘补的内容**标为草稿**（如加 `[待确认]`），用户确认后才转正。
> ⚠️ 如果能补却没补，只输出“缺失/不清楚/得分低”，视为本 skill 执行失败。

### 第 3 步：基于自补草稿评分

评分必须基于“原文件 + 自盘补上的 `[待确认]` 草稿”，逐维度打分，每维度列出：

- **得分**：X / 满分
- **判据**：为什么给这个分（指出具体哪句话/哪个位置满足/不满足）
- **已补**：本轮已经主动补了什么
- **待确认**：还需要用户确认什么
- **缺口**：差什么才到满分

输出评分摘要表：

```
## Goal 清晰度评分

项目：<项目名>
路径：<文件夹路径>
是否涉及取数：是/否

| # | 维度 | 得分 | 满分 | 达标率 | 已补 | 待确认 |
|---|------|------|------|--------|------|--------|
| 1 | 交付清单 | 16 | 20 | 80% | 已补协作平台文档交付形态草稿 | 确认案例数量 |
| ... | ... | ... | ... | ... | ... | ... |
| - | **总分** | XX | 100 | XX% | — | — |

判定：⚠️ 需追问补缺 / ✅ 可以开跑 / 🚫 回去补文档
```

### 第 4 步：追问（按达标率分流）

**追问范围规则**：

1. **先看各维度达标率**（得分 / 满分）
2. **达标率 < 80% 的维度**：全部追问——逐个列出「我已补的 → 请确认」+「我补不了的 → 追问你」
3. **所有维度 ≥ 80%**：只追问得分最低的 **3 项**的缺口
4. 用户回答后 → 补进文件 → **复评**（回到第 1 步重新盘点并打分）
5. 复评后仍 < 90 → 重复第 2-3 步，直到 ≥ 90 或用户决定暂停

> 每轮追问**只问当前该轮的缺口**，不把之前已确认的再问一遍。追问用编号列表，方便用户逐条回复。

### 第 5 步：放行判定

- 总分 ≥ 90 → 输出：

```
## ✅ 可以开跑

项目：<项目名>
最终评分：XX / 100

| 维度 | 得分 |
|------|------|
| ... | ... |

各维度均已达标，可以发起 Goal 模式。
```

## 注意事项

- **只读不改原始资料**：评分过程中读 `资料文件夹/` 下的内容做参考，但不修改原始资料
- **自盘草稿要标清**：自盘补进 goal.md / To-Do / spec / `_goal_gate_draft.md` 的内容必须标 `[待确认]`，用户确认后才转正
- **不替代 task-analyzer，但会调用它**：task-analyzer 管待办工具任务的五要素分析+写回，goal-gate 管项目文件的评分+闸门。v1.2 起 goal-gate 的第 0 步**复用** task-analyzer 的检索/关联能力把相关任务并成输入，但**评分与放行结论仍由 goal-gate 自己出**，不把闸门交给 task-analyzer
- **第 0 步是前置而非可选**：只要线索里有待办工具任务或外部素材引用，就必须先做「关联合并 + 取料」再评分；能推断却跳过，视为执行失败
- **取料有边界**：本步只取"已经存在"的资料（文档/网页/已有数据），不在评分阶段真跑取数 SQL；真执行放到 ≥90 之后的链路。**但字段实证不算"真跑取数"**——DESCRIBE 必须在评分前做掉，否则维度 3 无从判分
- **取数 BRD 是评分对象**（v1.4 新增）：涉及取数的项目，BRD 必须存在且经判定（需求清晰 / 字段来源清晰 / 时间粒度 / 一致性）；"有 BRD 就算过关"不成立，判的是清晰度
- **字段必须实证，禁止凭名猜**（v1.3 新增）：涉及取数的维度 3，只要出现未实证字段、或同义字段未写取舍理由，该项即判不合格并回退重补。教训：曾用「商机首个门店归属人」`create_first_store_owner_id` 去代表「任务归属人」，两字段 15,948 条不一致，导致结论推翻、反复返工
- **复评用最新文件**：每轮追问补完后复评，必须重新读文件（不靠内存缓存），确保评分基于最新内容
- **禁止懒评分**：低分维度必须伴随主动补全文案和确认问题；只给分、不补草稿、不问确认，判定为执行失败
