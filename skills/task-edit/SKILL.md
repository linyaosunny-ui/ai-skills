# task-edit - 待办工具任务安全编辑

> **一句话**：改任务字段（尤其标签）必须走「**先读 → 本地合并 → 整体写回**」，绝不直接 `--tags "新值"`。
> 因为 `dida task update --tags` 是 **覆盖**（非追加），直接写会**丢光任务原有标签**。

## 使用场景

- 「给这个任务加个标签」「标签打错了改一下」——标签替换/合并
- 批量修字段：改标题、补日期、调优先级、改截止时间
- 标签体系整理后，回填/修正存量任务
- 任何要动 `dida task update` 的场合——直接传 `--tags` 会覆盖丢标签，本 skill 是安全通道

## 实战案例

**改错标签（最常见的翻车现场）**：任务原本贴着 `工作`、`风控` 两个标签，只想把 `风控` 换成 `规则制度`。

> ❌ 直接 `dida task update <id> --tags "规则制度"` → `工作` 被一起覆盖删除。
> ✅ 三步法：① 读全量 `[工作, 风控]` → ② 本地合并 `[工作, 规则制度]` → ③ 整体写回 → ④ 回读核对（原标签在、新标签生效）。

## 核心默会知识（改任务前必读）

| # | 坑 | 正确做法 |
|---|---|---|
| 1 | `--tags` 是**覆盖**不是追加 | 必须先 `get` 读全量 tags → 本地合并 → 再整体写回 |
| 2 | `task update` 必须**同时**给位置参数和 `--id` | `dida task update <taskId> --id <taskId> --project <projectId> ...`，少一个报错 |
| 3 | 多行 `--content` 会被截断 | 写 content 一律用 **Python API**（禁 CLI） |
| 4 | 时区 | 写日期带 `+08:00`；读存储值 **+8 小时** |
| 5 | 清单是**工作流状态**（待跟进/跟进中/待审核），不是模块 | 改模块只能改**标签**，别改清单 |

## 标签编辑三步法（必须）

```
① 读    dida task get <projectId> <taskId> --json     → 拿到现有 tags
② 合并  现有 tags + 要加的 tags − 要删的 tags          → 去重、保序
③ 写回  dida task update <taskId> --id <taskId> --project <projectId> --tags "<合并后>"
④ 校验  dida task get <projectId> <taskId> --json     → 确认标签正确、无丢失
```

> 标签必须取自 `task-analyzer/task-tags.json`（唯一真相源）；新标签入库前先问用户。
> 打标纪律：**L1（工作/个人/家庭…）+ L2（模块）成对**，一条至少 1 个 L1。

## 十三项四证核对（改完必查）

改完任务后逐项确认，防止改坏：

| # | 核对项 | 方法 |
|---|--------|------|
| 1 | title 未变（若本次不改） | get 回读比对 |
| 2 | **tags 未丢** | 回读，确认原标签仍在 |
| 3 | 新增标签已生效 | 回读，确认存在 |
| 4 | projectId 未变 | 回读 |

## 执行流程

1. **定位任务**：用户给链接/ID → 解析出 `projectId` + `taskId`。
2. **读现状**：`dida task get <projectId> <taskId> --json`。
3. **确定改动**：只改用户明确要改的字段，不动其他。
4. **标签走三步法**（若涉及标签）。
5. **content 改动用 Python API**（若涉及）。
6. **写回 + 回读校验**（四证核对）。
7. **反馈**：展示「改动前 → 改动后」。
