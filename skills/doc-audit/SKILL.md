# doc-audit — 生成检核文档 Skill

**核心定位**：当用户说"生成检核"时，回顾本次对话中生成的所有文档/方案及其要求，生成一份标准化的《检核文档》，供检核agent独立审核。

---

## 何时使用

**触发词**: 「生成检核」「出个检核」「生成检核文档」

> ⚠️ **注意**：「检核一下」已被 `skill-audit` 占用，请勿使用此触发词调用 doc-audit。如需检核已生成的检核文档，请使用「检核一下」调用 skill-audit。

**前置条件**:
- 本次对话中已生成文档/方案
- 用户明确要求生成检核

---

## 完整工作流程

```
用户: "生成检核"
    ↓
【Step 0】查验待办工具任务描述（前置动作）
    - 用 MCP `dida task get` 读取对应任务，完整 content 含「五要素」+「【会话反馈】」记录
    ↓
【Step 1】回顾对话历史
    - 提取用户原始需求/背景说明
    - 提取文档/方案的要求描述
    - 识别所有生成的文件及其路径
    ↓
【Step 2】识别重点检核项
    - 回顾用户明确要求的、不能妥协的、一定要有的部分
    - 标记为【重点检核项】
    ↓
【Step 3】生成排查清单
    - 对每个生成文件：路径 + 目的 + 是否达成
    ↓
【Step 4】输出检核文档
    - 保存到与文档同一文件夹
    - 命名：【检核】-xxx事项-日期.md
```

## 检核文档标准结构

### 命名规范

```
【检核】-[事项名称]-[YYYYMMDD]-v[版本号].md

示例:
【检核】-业务开启项目方案-20260528-v1.md
【检核】-meeting-minutes skill创建-20260528-v1.md
```

> **版本号规则**：首次检核为 v1，后续递增（v2、v3...）。如已有同名文件，系统自动递增版本号。

### 存放位置

| 交付物类型 | 存放位置 | 判断依据 |
|------------|----------|----------|
| **Skill 类** | `{WORKSPACE}/PRD/检核文档/` | 文件路径包含 `{WORKSPACE}/AIAgents/skills/` |
| 普通文档/方案 | 与生成的文档/方案**同一文件夹** | 其他情况 |
| **多文件分散** | 优先与核心文档同一文件夹；若无核心文档，选择主要文档所在文件夹 | 无法判断核心文档时 |

> ⚠️ 如多个文件在不同文件夹，选择主要文档（如PRD/需求文档）所在文件夹存放检核文档。

### 文档内容模板

| 章节 | 内容说明 |
|------|----------|
| **0. 检核说明** | 角色声明、禁止事项、正确做法、检核流程、检核原则 |
| **0.1 检核思维要求** | ⚠️ 强调不能仅对照文档，要主动思考 |
| **1. 背景说明** | 用户原始背景信息（任务来源、业务场景、用户身份等） |
| **2. 需求描述** | 用户明确提出的需求（核心目标、输出要求、约束条件等） |
| **3. 重点检核项** | 用户强调的不能妥协的部分（表格：检核项/来源/判断标准） |
| **4. 排查清单** | 每个文件：路径/类型/目的/待检核项 |
| **5. 冗余表达排查** | 预留表格框架 |
| **6. 一致性核查** | 预留表格框架 |
| **7. 检核结论** | ⚠️ 留空 — 由检核Agent独立填写 |
| **8. 检核操作指引** | 执行步骤 + 禁止事项 + 修改建议格式要求 |

### 0. 检核说明 — 固定话术模板

```markdown
## 0. 检核说明

> **角色声明**：本文档由编写Agent生成，用于辅助检核Agent独立审核。
>
> **⛔ 禁止事项**：检核Agent不得编写Skill、不得编写目标文档、不得创建/调整/删除文件。
>
> **正确做法**：检核Agent仅做检核评估，输出检核结论和修改建议（如有问题）。
>
> **检核流程**：阅读背景→对照重点检核项→逐项排查→检查冗余→一致性核查→输出结论→给出建议。
>
> **检核原则**：挑剔、端到端验证、不轻信表面交付。
```

## 执行步骤详解

> 完整流程见上方"完整工作流程"图，以下为各步骤详细说明。

### Step 0: 查验待办工具任务描述（前置动作，必做）

> ⚠️ **任务描述是"唯一事实来源"**：检核方向的依据 = 待办工具任务描述最新 content（五要素 + 各轮【会话反馈】），而非仅凭对话记忆。

| 操作 | 说明 |
|------|------|
| 定位任务 | 确认本次交付物对应的待办工具任务（id / projectId） |
| 读取完整 content | 用 MCP `dida task get <projectId> <taskId>` 读取，避免截断 |
| 提取五要素 | 背景说明 / 任务交付物 / 交付标准 / 参考资料 / 执行建议及补充信息 |
| 提取交互过程 | 复盘任务描述中的【会话反馈】段（含时间戳），识别各轮补充/修改/强调 |
| 落地到检核文档 | Step 1 提取背景→需求→重点检核项时，以任务描述为准，对话历史仅作补充交叉参考 |

> **来源优先级**：待办工具任务描述（五要素 + 会话反馈） > 本次对话历史。若两者冲突，以任务描述为准并标注。

### Step 1: 回顾对话历史

**⚡ 前置动作：主动确认检核方向（无法从对话推断时必问）**

回顾对话后，判断以下 2 项是否已明确：

| 判断项 | 已明确？ | 兜底行为 |
|--------|---------|---------|
| 这份交付物**最核心的约束**是什么？（格式规范 / 业务正确性 / 可执行性 / 受众接受度） | 对话中有用户明确表述 → ✅ 直接提取 | 对话中**没有**明确表述 → 必须问用户 |
| 用户**最在意的 1-2 件事**是什么？ | 对话中有强调词（"一定" "必须" "不能"）→ ✅ 直接提取 | 没有强调词 → 必须问用户 |

**判断逻辑**：
- IF 两项都能从对话中提取 → 直接进入信息提取表格，无需打断用户
- IF 任一项无法从对话推断 → 先问用户以下问题，再继续：

  > 「这份 [交付物名称] 最核心的要求是什么？以及你最在意哪 1-2 件事？」
  > （用户回答后继续 Step 1，将答案作为重点检核项的最高优先级来源）

> **历史教训（6/4）**：检核文档的"重点检核项"靠推断生成，方向跑偏，skill-audit 再严格也没用。**推断 ≠ 用户真正在意的。**

| 信息类型 | 提取方式 |
|----------|----------|
| 背景说明 | 回顾用户首次提出需求时的描述 |
| 需求描述 | 回顾用户明确提出的要求 |
| 重点检核项 | 回顾用户强调的"一定要有的"、"不能妥协的"部分 |
| 生成文件 | 回顾本次对话中创建/修改的所有文件 |

**重点检核项识别规则**：

| 用户表述 | 是否为重点检核项 |
|----------|-----------------|
| "一定要有的" / "不能妥协的" / "必须包含" / "核心要求" / "重点" | ✅ 是 |
| "最好有" / "如果可以的话" | ❌ 否（可选） |

**⚠️ 信息不足时的兜底处理**：

| 场景 | 处理方式 |
|------|----------|
| 无法提取背景说明 | 在【背景说明】中标注"[信息不足，需补充]"，并在检核结论中建议用户补充 |
| 无法识别重点检核项 | **不得直接推断**，必须先问用户（见上方前置动作）；用户确认后再填写重点检核项 |
| 对话中未生成任何文件 | 提示用户"本次对话未生成可检核的文档/方案"，结束流程 |

### Step 2: 识别重点检核项

| 操作 | 说明 |
|------|------|
| 回顾用户明确要求 | 提取用户强调的"不能妥协"、"一定要有的"部分 |
| 标记重点检核项 | 在检核文档中标注为【重点检核项】，后续逐条对照 |

### Step 3: 生成排查清单

| 操作 | 说明 |
|------|------|
| 遍历所有生成文件 | 对每个文件记录：路径、类型、目的 |
| **⚠️ 禁止预先判断** | 不得填写"是否达成"，仅列出文件基本信息 |
| 记录待检核项 | 列出需要检核Agent检查的具体内容（如"检查文件是否包含XX功能"） |
| 提供证据材料 | 提供文件路径、代码片段等供检核Agent参考，但不做结论 |

> **⚠️ 重要原则**：生成检核文档的agent **不得预先判断**任何内容是否达成，所有检核结论必须由检核Agent独立填写。

### Step 4: 输出检核文档

> ⚠️ **重要：生成后必须立即将完整版检核文档的文件绝对路径发送给用户**，格式：`📄 检核文档已生成：[绝对路径]`。方便用户后续将文档交给检核Agent审核。

**存放位置规则**：

| 交付物类型 | 存放位置 | 判断依据 |
|------------|----------|----------|
| **Skill 类** | `{WORKSPACE}/PRD/检核文档/` | 文件路径包含 `{WORKSPACE}/AIAgents/skills/` |
| 普通文档/方案 | 与生成的文档/方案同一文件夹 | 其他情况 |

**命名格式**：`【检核】-[事项名称]-[YYYYMMDD]-v[版本号].md`

示例：
- `【检核】-业务开启项目方案-20260528-v1.md`
- `【检核】-meeting-minutes skill创建-20260528-v1.md`
- 同一事项多次检核时递增版本号：v1 → v2 → v3

**版本号自动递增规则**：
1. 生成前检查目标文件夹是否已存在同名文件
2. 如存在，取最大版本号，递增生成（如已有 v1、v2，则生成 v3）
3. 如不存在，默认生成 v1

**⚠️ 生成后必须输出文件地址**：检核文档保存完成后，必须立即将完整版的检核文档**文件绝对路径**发送给用户。格式如下：

```
📄 检核文档已生成：[文件绝对路径]
```

> **目的**：确保用户知道检核文档的确切位置，方便后续将文档交给检核Agent审核。

---

### ⚠️ 异常处理说明

| 异常场景 | 处理方式 |
|----------|----------|
| **对话中未生成任何文件** | 提示用户"本次对话未生成可检核的文档/方案"，结束流程 |
| **部分文件生成失败** | 在排查清单中标注失败文件及原因，检核结论中说明"部分达成" |
| **文件路径变动/不存在** | 在排查清单中标注"文件路径不存在"，建议用户确认路径后重新生成检核 |
| **用户未明确要求检核** | 提示用户"请明确说'生成检核'或'检核一下'以触发检核流程" |
| **同一事项多次检核** | 使用版本号区分（v1、v2、v3...），避免覆盖旧检核文档 |

---

## Step 5: 输出检核指令（供发送给检核Agent）

**⚠️ 重要：每次生成检核文档后，必须输出以下格式的检核指令，供用户直接发送给检核Agent**

生成检核文档后，按以下格式输出指令（仅输出指令本身，不要输出其他内容）：

```
使用 skill-audit 对以下检核文档进行完整检核：

[检核文档的绝对路径]

检核完成后，修改该检核文档中的【检核结论】章节，填写检核结果。
```

### 8. 检核操作指引

> ⛔ **强制前置步骤（不可跳过）**：开始检核前必须调用 skill-audit，读取七大模块方法论。未执行此步骤的检核视为无效，必须重做。
>
> **Skill 绝对路径**：`{WORKSPACE}/AIAgents/skills/skill-audit/SKILL.md`
>
> 检核Agent **必须**在开始任何检核工作前：
> 1. 调用 `skill-audit` Skill
> 2. 完整阅读其 SKILL.md 中的七大模块方法论
> 3. 严格按照七大模块执行检核
>
> **跳过 skill-audit 方法论的检核视为无效，必须重做。**

### 📋 检核模式选择

| 模式 | 触发方式 | 适用场景 |
|------|----------|----------|
| **完整版检核** | 默认模式 | 需要全面检核，包含所有章节和详细分析 |
| **简版检核** | 用户说"简版检核"或"快速检核" | 只需查看重点检核项和结论，快速确认是否达标 |

**简版检核输出内容**（仅包含以下章节）：
- 0. 检核说明（精简版）
- 3. 重点检核项（仅列出，不展开）
- 7. 检核结论（仅结论 + 综合建议）

> ⚠️ 简版检核仍**必须调用 skill-audit**，但输出结果精简，跳过冗余排查和一致性核查的详细表格。

---

检核Agent拿到本文档后，按以下步骤执行：

**【前置强制步骤】**
0. **🔥 必须调用 skill-audit Skill** — 加载 [skill-audit](../skill-audit/SKILL.md) 的方法论，理解七大模块检核框架

**【正式检核步骤】**
1. **阅读**【背景说明】和【需求描述】，理解原始需求
2. **逐条对照**【重点检核项】，确认是否满足
3. **逐项排查**【排查清单】中的每个文件
4. **检查冗余**，识别啰嗦重复的表达
5. **一致性核查**，检查前后不一致和数据计算错误
6. **输出结论**，按【检核结论】模板填写
7. **给出建议**，如有问题明确指出修改方向

### ⚠️ 检核思维要求（重点强调）

检核Agent **不能仅停留在对照文档列出的事项**，必须主动思考：

| 思考维度 | 具体内容 |
|----------|----------|
| **背景理解** | 从任务来源、业务场景出发，理解为什么需要做这件事 |
| **用户需求** | 分析用户真正想要解决什么问题，而不仅仅是表面需求 |
| **重点强调部分** | 深入理解用户反复强调的部分，思考其背后的意图 |
| **主动评估** | 基于以上理解，评估现有内容和方案是否存在不足、遗漏、偏差或可改进空间 |

**检核Agent应自问**：
- 如果我是用户，看到这个方案会觉得哪里不够？
- 是否有场景被遗漏？是否有风险未考虑？
- 文档/方案的逻辑是否自洽？是否真正解决了核心问题？
- 是否有更好的表达方式或更优的实现方案？

### 📌 必须结合 skill-audit 执行检核

**这是强制要求！** 检核Agent **必须**调用 [skill-audit](../skill-audit/SKILL.md) Skill，严格按照其七大模块方法论执行检核：

| 模块 | 用途 | 必须执行 |
|------|------|----------|
| **模块一：规范完整性检核** | 检查SKILL.md格式规范 | ✅ 必做 |
| **模块二：能力实现度检核** | PRD vs SKILL.md交叉对比 | ✅ 必做 |
| **模块三：场景覆盖度分析** | 主动推断用户可能遇到的各种场景 | ✅ 必做 |
| **模块四：实战流畅度检查** | 10维度检查执行是否顺畅 | ✅ 必做 |
| **模块五：修改建议** | 按文件分组给出编号步骤 | ✅ 必做 |
| **模块六：修改完成清单** | 汇总为可勾选清单 | ✅ 必做 |
| **模块七：端到端流程回顾** | 模拟完整链路验证衔接 | ✅ 必做 |

**⚠️ 警告**：
- 跳过 skill-audit 的检核视为**不合格**
- 仅做表面对照而不使用skill-audit方法论的检核视为**敷衍**
- 检核Agent应主动调用skill-audit，而不是等待用户提醒

### ✅ 一致性核查要点

检核Agent需自行核对以下内容：

| 核查类型 | 检查内容 | 示例 |
|----------|----------|------|
| **前后不一致** | 同一概念/术语在不同章节的表述是否一致 | 前文说"业务"，后文说"站外" |
| **数据计算错误** | 数据计算逻辑是否正确，结果是否准确 | 百分比计算错误、求和错误 |
| **逻辑矛盾** | 不同章节的结论是否相互矛盾 | 前文说"已完成"，后文说"待完成" |
| **引用错误** | 引用的文件/数据/链接是否正确 | 引用了不存在的文件路径 |
| **格式不一致** | 同一类型内容的格式是否统一 | 日期格式混用（2026-05-28 vs 2026/05/28） |

**一致性核查模板**：

```markdown
## 6. 一致性核查

| # | 位置 | 问题类型 | 问题描述 | 正确内容 |
|---|------|----------|----------|----------|
| 1 | [文件+章节/行号] | 前后不一致/数据错误/逻辑矛盾 | [具体问题] | [正确内容] |
| 2 | ... | ... | ... | ... |

**如无问题**：✅ 本次交付无前后不一致或数据计算错误
```

### ⛔ 检核Agent禁止事项

| 禁止行为 | 说明 |
|----------|------|
| **禁止编写 Skill** | 检核Agent不得自己进行 Skill 的编写工作 |
| **禁止编写目标文档** | 检核Agent不得自己进行目标文档的编写工作 |
| **禁止创建/调整/删除文件** | 除非用户明确要求生成《调整建议》文档，否则不得进行任何文件操作 |
| **禁止直接修改** | 只做检核，不做修改 |

### ✅ 修改建议格式要求

修改建议必须具体到以下三个要素：

| 要素 | 说明 | 示例 |
|------|------|------|
| **哪个文件** | 文件的绝对路径 | `{WORKSPACE}/AIAgents/skills/doc-audit/SKILL.md` |
| **哪个章节** | 具体到章节/行号 | 第125行，"三、重点检核项"章节 |
| **修改原因** | 说明为什么要改 | 该检核项缺少判断标准，无法验证是否达标 |

**修改建议模板**：

```markdown
### 文件：[文件路径]

1. **章节**：[章节名称]
   - 第X-Y行（或指出什么表达内容），将 `xxx` 改为 `yyy`
   - **原因**：[修改原因]
```

## 附录：检核Agent修复操作规范

### 🔧 检核发现问题后的修复流程

当检核Agent发现目标文件有问题时，必须使用 `opencode-runner` Skill 进行修复：

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | **发现问题** | 检核Agent完成检核，输出【检核结论】和【修改建议】 |
| 2 | **触发修复** | 检核Agent直接调用 `opencode-runner` Skill |
| 3 | **执行修复** | 使用 `opencode-runner` 的 `opencode run` 命令修复问题 |
| 4 | **默认模型** | 使用当前环境的默认模型（不写死具体型号；如遇复杂修复可升级更强模型） |
| 5 | **反馈记录** | 修复完成后记录到对应PRD的变更记录 |

### opencode-runner 使用示例

```
使用 opencode-runner 执行以下修复：
- 文件路径：{WORKSPACE}/AIAgents/skills/doc-audit/SKILL.md
- 修复内容：[检核发现的问题描述]
- 使用模型：当前默认模型
```

### ⚠️ 重要原则

- **检核与修复分离**：检核Agent负责发现问题，`opencode-runner` 负责执行修复
- **模型选择**：使用当前环境默认模型；如遇复杂修复可临时升级到更强模型
- **修复后验证**：修复完成后，检核Agent应重新检核确认问题已解决
