# ai-content-verify — AI 内容真伪核验工作流编排器

> **核心原则：挑剔**  
> 不满足于「表面上看起来在核验」。每次核验必须端到端走完 4 步法（搜作者 → 验证仓库 → 互动分析 → 作者自承限制），最后给出"可引用 / 可学习 / 不可信"三档结论。不轻信作者自述，必须独立验证。

> **定位**：串联 5 个现有 Skill（defuddle / agent-browser / gh-cli / find-skills / skill-audit）+ 1 个新增"AI 营销 vs 真实技术"4 维度评估框架，不重造轮子。

> **异常处理**：当输入是非 AI 内容（如纯生活分享、纯娱乐新闻），应明确告知用户不在本 Skill 评估范围。

## 一、概述

本 Skill 解决「外部 AI 神器分享到底是真技术还是营销包装」的核验问题。通过 4 步法 + 4 维度评分 + 与现有 Skill 体系对比，端到端输出三档结论（可引用 / 可学习 / 不可信）和 8 段标准核验报告。

---

## 二、何时使用 / 何时不使用

### 何时使用
- 论坛 / 公众号 / Reddit 上看到一篇 AI 神器分享，想判断真假 → 「核验 https://xxx 这篇文章」
- 群友转了一个 GitHub 项目链接，想知道作者背景 → 「评估 https://github.com/xxx 是不是真实项目」
- 已经手动评估过，想沉淀方法论 → 「按 ai-content-verify 跑一遍」
- 看到疑似营销包装的 AI 文章 → 「XX 帖子是不是营销包装」

### 何时不使用
- ❌ 非 AI 内容（纯生活分享、娱乐新闻、政治评论）→ 不在评估范围
- ❌ 只需要作者联系方式或邮箱 → 用 `lark-contact`
- ❌ 需要写代码实现某个 AI 工具 → 用对应的工程类 Skill
- ❌ 需要 git ls-remote 或 API 查询 → 委托 gh-cli（不替代）

### 3.0 Step 0：检索历史案例

**操作**：在本次核验正式执行前，读取 `{WORKSPACE}/Memory/ai-content-verify-cases/cases.json`（若不存在则跳过 Step 0），从输入 URL 或标题中提取关键词，搜索已有案例库。

**匹配规则**：
- 从输入内容中提取 3-5 个核心关键词（如产品名、作者、技术术语）
- 逐条遍历已有案例，命中的关键词 ≥ 2 个 或 由 Agent LLM 判定标题/URL 内容相似 → 视为"关联历史案例"
- 匹配结果写入最终报告的"关联历史案例"段

**JSON 案例库字段匹配示例**：
```python
# 伪代码逻辑
keywords = extract_keywords(input_url, input_title)
for case in cases_json["cases"]:
    matched = [k for k in keywords if k in case["keywords"]]
    if len(matched) >= 2:
        add_to_report("关联历史案例", case)
```

**异常处理**：
- 若 `cases.json` 不存在（首次运行），跳过 Step 0，直接进入 Step 1，报告中标注"历史案例库为空"
- 若 `cases.json` 解析失败（格式损坏），跳过 Step 0，报告中标注"历史案例库读取失败"

**验收标准**：100% 核验任务执行前都会检查 `cases.json`，无遗漏。

### 3.1 Step 1：抓取 + 清洗

| 输入类型 | 工具 | Fallback |
|---------|------|----------|
| 静态网页（博客/文档） | `defuddle` | `agent-browser` 截图+OCR |
| 动态内容（论坛 SPA） | `agent-browser` | 无 |
| GitHub 仓库 | `gh-cli`（git ls-remote + API） | `github-kb` |
| 纯文本粘贴 | 直接解析 | 无 |

**验收标准**：95%+ 静态页面成功抓取；GitHub 仓库存在性 100% 准确。

### 3.2 Step 2：4 步法评估

| 子步骤 | 操作 | 关键证据 |
|-------|------|---------|
| **2.1 搜作者 + 背景** | `WebSearch "<作者姓名> GitHub"` + 抓作者主页（`defuddle`） + 查 Google Scholar 论文 + 查组织成员列表（GitHub API `/orgs/{org}/members`） | 作者所属团队可信度评分（高/中/低） |
| **2.2 验证 GitHub** | `gh repo view <owner/repo>` + `gh api /repos/{owner}/{repo}` + `gh api /orgs/{org}/repos --paginate` + `curl -I https://raw.githubusercontent.com/<owner>/<repo>/<branch>/README.md` | 仓库存在性 + 内容匹配度 |
| **2.3 互动分析** | 抓评论区 + 分类「捧场 vs 技术讨论」 | 营销嫌疑度指标 |
| **2.4 抽自承限制** | 正则 `(?<![不无])(还[处于在]|[还仍].{0,4}不够|不太够|尚未|暂时|初步|alpha\|beta\|不稳定\|有.{0,4}限制\|存在.{0,4}问题)` + 句式模板「目前/现阶段 + 限定语」 | 至少捕获 80% 自承句 |

> **工具依赖说明**：`WebSearch` 需 Agent 内置 WebSearch 工具能力；`curl` 需系统命令可用。
> **异常处理**：若 `WebSearch` 不可用，改用 `defuddle` 抓作者主页 + GitHub API 查组织成员列表；若 GitHub API 返回 429（限流），等待 60 秒后重试，最多 3 次。

**案例参考**（来自 2026-06-14 某 AI 工具论坛帖）：
- 2.1：反查到 QuantaAlpha 组织（清华/北大/CMU/HKUST 真实团队）→ 作者背景可信
- 2.2：`git ls-remote` 三个仓库全部 Repository not found → 仓库不存在
- 2.3：107 赞 35 帖全是「牛牛牛」类捧场 → 营销嫌疑度高
- 2.4：抽出 4 条自承句（"Trae CLI 还处于 alpha"等）→ 作者坦诚

**Step 2 → Step 3 衔接映射规则**（避免主观判分）：
- **营销包装** ← Step 2.3 互动分析：捧场回复 ≥80% → 2-3 分；50-80% → 1 分；<50% → 0 分
- **技术原创** ← Step 2.1 作者背景 + Step 2.2 仓库 README：是否提出新概念/新方法
- **可验证性** ← Step 2.2 GitHub 验证：仓库不存在 → 0 分；仓库空 → 1 分；仓库有内容但与文章不符 → 2 分；完整 demo+数据 → 3 分
- **体系补足** ← Step 4 find-skills 查重：完全重复 → 0 分；微小补充 → 1 分；明显缺口 → 2 分；关键空白 → 3 分

### 3.3 Step 3：4 维度评分

**核心：每维度 0-3 分，总分 0-12 分。营销包装维度反向计分（越低越好）。**

| 维度 | 评分方向 | 0 分 | 1 分 | 2 分 | 3 分 |
|------|---------|------|------|------|------|
| **营销包装** | 越低越好 | 真实坦诚 | 轻度包装 | 明显营销 | 纯流量炒作 |
| **技术原创** | 越高越好 | 纯抄袭 | 缝合已有方案 | 有部分创新 | 原创方法论 |
| **可验证性** | 越高越好 | 仓库不存在 | 有仓库但内容空 | 仓库有内容但与文章不符 | 仓库+演示+数据齐全 |
| **体系补足** | 越高越好 | 完全重复现有 Skill | 微小补充 | 补足明显缺口 | 填补关键空白 |

**评分示例**（Codestyle 帖）：

| 维度 | 得分 | 依据 |
|------|-----|------|
| 营销包装 | 2 分 | 帖子可读性强，但回复全是捧场 |
| 技术原创 | 2 分 | Maven 坐标式索引 + 二阶段召回 有创新 |
| 可验证性 | 0 分 | 三个核心仓库全部 Repository not found |
| 体系补足 | 1 分 | Skill 五原则与现有体系微重合 |
| **总分** | **5** | → **不可信**（≤5） |

### 3.4 Step 4：体系对比（find-skills 查重）

调用 `find-skills` Skill 查询本地 `.claude/skills/` 目录，对比：
1. 是否有相同/相似主题的 Skill 已存在
2. 是否补足现有体系的明显空白
3. 是否值得新增一个 Skill（如是，给出 Skill 草稿建议）

### 3.5 Step 5：能力差距分析（v1.2 新增）

**触发条件**：仅当三档结论为「可引用」或「可学习」时执行；「不可信」直接跳过此步。

**目的**：回答"这个 AI 工具的能力，我现在的 Agent 体系缺不缺？缺多少？怎么补？"

**5 子步流程**：

| 子步骤 | 操作 | 工具 |
|-------|------|------|
| **5.1 提取能力宣称** | 从 Step 1 抓取的原文中，用 LLM 抽取工具宣称的「我能做 X」类能力点（3-10 个） | 主 Agent |
| **5.2 映射现有能力** | 对每个能力点，在当前 Agent 体系（Skill + SubAgent + MCP + 外部工具）找匹配 | `find-skills` + 读 `AGENTS.md` |
| **5.3 缺口分级** | 按缺失程度分：关键空白 / 一般缺口 / 微小补充 / 完全重复 | 主 Agent 判定 |
| **5.4 落地路径** | 针对每个缺口，给推荐落地方式：建新 Skill / 增强现有 Skill / 装 MCP / 用外部工具 / 不需要 | 主 Agent + `skill-requirements-discovery` |
| **5.5 部署决策** | 综合缺口等级 + 三档结论，给最终部署建议 | 主 Agent |

**5.4 判定"建新 Skill"后的交接链（v1.4）**：
一旦 5.4/5.5 得出"值得建新 Skill"，**不要在本 Skill 内直接写 SKILL.md**（§七安全约束禁止），而是按顺序交接：
1. 先查归档能否复用：`归档技能清单_2026-07-25.md` / `ls {WORKSPACE}/AIAgents/skills/_archived_skills/ | grep 关键词` —— 命中就复制回 `AIAgents/skills` 改用，流程结束。
2. 归档无现成 → 调用 `creating-skills` 正式创建（它自身入口也会再提醒先翻归档，双保险）。
3. 思路不清 → 先 `skill-requirements-discovery` 对话式厘清需求，再进 `creating-skills`。

**能力矩阵输出格式**：

| 工具宣称能力 | 现有体系对应 | 缺口等级 | 推荐落地方式 | 优先级 |
|-------------|------------|---------|-------------|--------|
| 自动核验 GitHub 仓库 | `gh-cli` (Skill) | 完全重复 | 不需要 | - |
| 自动生成营销评分 | 无 | 关键空白 | 建新 Skill `marketing-assess` | P0 |
| 自动抓评论区 | `agent-browser` (Skill) | 微小补充 | 增强现有 Skill | P2 |
| ... | ... | ... | ... | ... |

**部署决策输出规则**：

| 三档结论 | 缺口等级 | 部署决策 | 理由模板 |
|---------|---------|---------|---------|
| 可引用 | 完全无缺口 | **建议立即部署** | 真技术 + 能力已具备，可直接落地 |
| 可引用 | 有微小补充 | **建议部署 + 异步补足** | 真技术，缺口小不阻塞 |
| 可学习 | 有一般缺口 | **部分部署**：核心能力先落，其他暂缓 | 借鉴价值大于直接使用 |
| 可学习 | 关键空白 | **暂不部署**：先建缺失能力 | 工具本身有价值但体系未到位 |
| 不可信 | 任意 | **不部署** | 真伪不通过，部署无意义 |

## 四、三档结论判定规则

| 结论 | 总分区间 | 含义 | 后续行动 | **部署建议（v1.2）** |
|------|---------|------|---------|---------|
| **可引用** | ≥ 10 | 可直接用作工具或参考 | 含原始链接 + 验证截图 + 数据；归档到 `{WORKSPACE}/Knowledge/wiki/` | **建议部署**（先看 §3.5 能力矩阵） |
| **可学习** | 6-9 | 可学习设计哲学，但不直接使用 | 提取方法论要点 → `{WORKSPACE}/Knowledge/raw/articles/` 待 ingest | **部分部署**（核心能力先落） |
| **不可信** | ≤ 5 | 作者背景可疑 / 仓库不存在 / 纯营销包装 | 仅留报告存档，不引用 | **不部署** |

**判定要点**：
- **可引用门槛**：可验证性 ≥ 2 分（必须有仓库/数据可查）
- **不可信红线**：可验证性 = 0 分（一票否决，无论其他维度多高）
- **可学习特征**：原创 ≥ 1 分 且 总分 ≤ 9（说明有想法但落地不足）

## 七、操作安全约束

本 Skill 的 agent **只能**执行：
- 抓取/读取公开网页和 GitHub 仓库
- 调用 `defuddle` / `agent-browser` / `gh-cli` / `find-skills` 已有 Skill
- 输出 8 段核验报告到当前会话或用户指定路径

### JSON 案例库（v1.3 新增，替代目录式归档）

每次完成核验后，将结构化结果追加到 `{WORKSPACE}/Memory/ai-content-verify-cases/cases.json`。

**cases.json 结构**：
```json
{
  "cases": [
    {
      "id": "case_YYYYMMDD_NNN",
      "title": "核验文章标题",
      "url": "原始链接",
      "author": "作者/团队",
      "verified_at": "YYYY-MM-DD",
      "conclusion": "citable | learnable | untrusted",
      "total_score": 0,
      "scores": {
        "marketing": 0,
        "originality": 0,
        "verifiability": 0,
        "system_gap": 0
      },
      "keywords": ["关键词1", "关键词2"],
      "summary": "核验结论摘要（1-2 句）",
      "related_cases": []
    }
  ]
}
```

**案例库累积规则**：
- 每次核验完成后，立即追加一条到 `cases.json` 的 `cases` 数组
- `id` 格式：`case_YYYYMMDD_NNN`（NNN 为当天序号，从 001 开始）
- `keywords` 从输入 URL 和标题中提取 3-5 个核心关键词，确保后续检索可命中
- `related_cases` 初始为空数组，由 Step 0 检索时自动填充关联的 case id
- 若 `cases.json` 不存在，首次创建；若已存在，读取后追加，保留全部历史记录

**归档格式（可选）**：完整核验报告仍以 Markdown 归档到 `{WORKSPACE}/Memory/ai-content-verify-cases/reports/`，但案例库的主索引为 JSON 文件。
